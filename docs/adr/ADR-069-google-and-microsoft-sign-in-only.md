# ADR-069: Google and Microsoft sign-in only

## Status

Accepted

## Context

Players signed in with an e-mail address and a password (docs/adr/ADR-009), and account recovery sent codes by SMTP (docs/adr/ADR-032).
Recovery was removed by the `RemovePasswordRecovery` migration, but password sign-in and registration remained. The owner decided that players
sign in only with Google or Microsoft: no password is stored or checked, and no e-mail is sent.

The sibling product AtmosOS already signs players in with Google Identity Services and MSAL, sending the provider's ID token to the server, which
verifies it. This decision copies that approach, with names that match Nosum.

## Decision

1. **The server decides identity from a verified ID token.** The web client obtains an ID token from Google (Google Identity Services) or Microsoft
   (MSAL, popup) and sends it in `ExternalSignIn` or `LinkExternalIdentity`. `IExternalTokenVerifier` (`Nosum.Abstractions/Identity`) checks it in
   `Nosum.Infrastructure/Identity`: the RS256 signature against the provider's published keys (cached one hour, refetched at most once a minute), `alg`
   must be `RS256`, `aud` must be the configured client id, `iss` must be the provider's issuer, and `exp` and `nbf` are checked with two minutes of
   clock skew. A token that fails any check, or a provider with no client id configured, gives `AccountStatus.InvalidIdToken`. The check runs on the
   BCL only; no token library is added.
2. **The identity key is the provider and its stable subject.** Google: `sub`. Microsoft: `oid`, else `sub`. For Microsoft the issuer must be the
   token's own tenant (`tid`), and a server configured for one tenant accepts only that tenant. The stored key is `external_logins (provider, subject)`,
   unique. The e-mail is kept on `players.email` for display only and never finds an account.
3. **Accounts.** The first sign-in with an unknown identity creates a registered player with `IsGuest = false` and a neutral nickname
   (`guest-NNNN`). The player renames it with `SetNickname`; the first rename is free (the 24-hour wait starts after it). A guest links an identity
   with `LinkExternalIdentity` and chooses a nickname in the same request. The player id, state and data are kept, the guest's session is revoked, and
   a new one is issued. A link is refused when the guest is not a guest (`NotGuest`), the identity belongs to another account (`IdentityTaken`), or the
   nickname is taken.
4. **Wire (protocol version 9, docs/adr/ADR-032 D3 and the append-only rule).** New opcodes `ExternalSignIn` (`0x1009`) and `LinkExternalIdentity`
   (`0x100A`), both answered by `AccountResult`. The identity token is at most 8 KB and travels in an encrypted frame (`[PacketEncryption(true)]`).
   `Register` (`0x1001`), `Login` (`0x1002`), `UpgradeGuest` (`0x1006`), `ChangePassword` (`0x11EE`), `PasswordResult` (`0x11E0`),
   `RequestPasswordReset` (`0x11F0`) and `ConfirmPasswordReset` (`0x11EF`) are retired: their classes stay reserved with no fields, their opcodes are
   never reused, and the server has no handler. `AccountStatus` codes `InvalidIdToken` (20) and `IdentityTaken` (21) are added; codes 1-4 are retired.
5. **Data.** Migration `ExternalSignInOnly` drops `players.password_hash`, `players.normalized_email` and its unique index, and creates
   `external_logins`. `players.email` stays, widened to 254 characters. The migration is generated by `dotnet ef`.
6. **Configuration.** The server reads `NOSUM_GOOGLE_CLIENT_ID`, `NOSUM_MICROSOFT_CLIENT_ID` and `NOSUM_MICROSOFT_TENANT` (`common` by default);
   `deploy/compose.yaml` passes them. The web client reads the same two client ids from `ExternalSignIn` in its `appsettings.json`, which are public
   values, not secrets. A provider with an empty id is off: its button is disabled and its tokens are refused.
7. **Rate limits.** Sign-in attempts are limited to 15 per address per minute (`sign-in-attempt`, replacing `login-attempt`). The per-day
   new-account limit (docs/adr/ADR-032 D6) now counts guest starts only: a sign-in creates an account only with a real provider identity.
8. **E-mail is not sent anywhere.** The SMTP sender and its settings were removed earlier; the host no longer reads any `NOSUM_SMTP_*` setting.

### Not in this decision

- **Existing password accounts** keep their rows but have no identity, so they cannot sign in after this change. An automatic link by e-mail address
  was rejected: an address the provider reports is not proof of the account, and this decision never trusts the e-mail as a key. A one-off
  migration tool, if the owner wants one, needs its own decision.
- A second provider on an account, and unlinking an identity.
- Replay protection of ID tokens: a token is accepted until its own expiry (about an hour), as the provider issues it. The channel is encrypted.
- Account recovery for a lost provider account.

## Consequences

- Sign-in needs the provider's keys, fetched at most hourly; a provider outage refuses sign-in and never trusts a token.
- The server holds no secret for sign-in: the client ids are public, and no password hashing remains.
- Clients and server ship together (protocol version 9). A pre-9 client cannot sign in.
- The retired packets stay in the protocol as empty classes, so their opcodes cannot be reused by accident.
- Running the integration tests needs no network: the tests use a fake verifier, and the verifier tests use locally generated RSA keys.
